# Review of the first round — 2026-09-22

Six reviewers verified the five builders' status reports against the code and
the checks: one per stream, one for the seams between them. Every claim was
read against the file it names; every check the reports name was re-run where
the machine allowed. Nothing was edited, and the four session worktrees are
untouched so the same sessions can take the second round.

Headline: **the work is real and the reports are largely honest.** Every commit
is on dev, main and origin in all three repos; nothing was clobbered in the
shared files; no temp branch reached GitHub. Every suite the builders named
passes, and two counts were understated rather than overstated. Three seams do
not yet meet, two contracts shipped helpers with no caller, and each stream
has defects its own Left list does not mention. Those are the second round.

## Verdicts by stream

### WS-A — individual mode

Verified: C1 exactly as the README states, one parser and five callers. C3
table and helper exactly as stated, `share`/`revoke` need `owner`, `visible`
has no admin branch. Registration in individual mode with the organisational
branch byte-identical below it. Per-user Drive root and per-person quota keys;
a stranger's node is unreachable. Harness and proofs. 121 assertions pass,
including `smoke:individual` on a two-tenant core.

Defects the Left list does not mention:

1. **`grant-full-access.js` is mode-blind** (`api/core/scripts/grant-full-access.js`,
   called by `provisionOwner` on every first-run owner claim). In an
   organisational instance it creates every `_individual` role and
   `platform_operator`; in an individual instance it hands one customer
   `_admin`, `_manager`, `_staff` and `platform_operator`. This defeats C2 in
   both directions.
2. **An individual-mode instance is permanently `orphaned`.** Nobody holds
   the admin keys, so `instanceState()` never reaches `ready`; the
   unauthenticated setup state publishes a live headcount of the public
   instance and keeps the recovery doors armed for ever.
3. **No aggregate storage cap.** Each person's quota row is created at the
   instance's whole licensed limit.
4. **Operator enumeration.** `listPeople` with an empty query returns every
   registered address, fifty at a time — a sixth act the spec's five do not
   include. An operator can also issue a set-password link for another
   operator's row, after which that row passes the operator gate by password.
5. **Two promises without callers.** `registerOwnerRelation` is called by
   nothing in production, so Sign's `sender_user_id` and `owner_user_id` are
   not registered as owner relations. `storeSessionAllowance` is not called by
   WS-D's redeem, so the operator's allowance panel is always empty.
6. **Sign is not offered.** `OFFERED_TO_INDIVIDUALS` is `drive, workspace`.
   `sign_individual` already passes the api-pro gate (WS-B's ask is moot); the
   only missing piece is Sign's proof under WS-A's harness, which is WS-A's to
   write.
7. Twenty-two files outside the owned list, several undisclosed, including
   `api/platform/src/identity.js`, which the README said stays as it is.

### WS-B — one Sign app

Verified: the guided path end to end, consuming `@rutba/docpack` directly;
the permissions adapter matches the helper's names and now delegates to it;
settings page in organisational mode only; the site hands over with
`from=sign-site` and a pack intent; stale claims gone bar one correct line;
estate map and the Sign door. Suites: packs 6, handoff 6, mirror 7, drift 2
with the path count still 30, `smoke:sign` 262, estate-map 10, site typecheck.

Defects the Left list does not mention:

1. **Keys and policy reads are ungated.** The report says the engine's admin
   gates refuse keys and webhooks in individual mode; only the writes are
   gated. `listApiKeys` and `getPolicy` scope by organisation, which in
   individual mode is one shared organisation, so every individual would read
   every key name. A cross-person leak the day Sign is offered.
2. **The pack intent never arrives, twice over.** Global auth's plan pattern
   drops `prepare:<pack>:<CC>` at the front door (confirmed), and even when auth
   carries it, the Sign door's `landingFor` prefers the explicit `next=/` the
   hub always sends. Both ends need a change; the auth end is WS-D's file.
3. **Migration 112 outside the owned list**, applied to the shared dev database
   from an unmerged worktree, which stopped every core booting from the main
   checkout until the merge, and took the ordinal WS-D held.
4. **No backfill.** Templates from before the migration carry a null owner and
   become invisible and undeletable in individual mode.
5. Its own README's seam row is stale (WS-E noted it; the file is WS-B's).

### WS-C — provisioning

Verified: the reaction per provisioner value; worker gate routes with
`FOR UPDATE SKIP LOCKED`; C4 record and the personal-organisation rule;
invitations after both outcomes with a 10 s timeout; console routes and page;
worker steps, schema-only clone, migrate in a child process, resume from
step; C7 doors on the real verifier with no stub. Strapi 85 tests,
`check:provisioning` 35, `smoke:tenants-door` 38, `smoke:tenant-directory` 49,
worker tests 27 when run by file.

Defects the Left list does not mention:

1. **The lease is dead.** `claim` requires `status: 'queued'` but a claim sets
   `running`, so `claimedUntil < now` never matches and nothing sweeps stale
   jobs. A worker that dies wedges its job for ever. The attempt ceiling lives
   only in the worker; `failJob` re-queues without bound.
2. **`withoutCredentials` is overclaimed.** It is applied to three fields on
   success, not to job `input` and `state`, which are stored raw; its denylist
   misses `url`, `dsn`, `apiKey`, `privateKey`, `bearer` and anything inside
   an array.
3. **A failed `migrate` leaves the half-built database**, `rolling_back` is
   never set, and `ensureMysql` short-circuits on any existing table, so a
   partial clone is never completed either.
4. **`npm run check` in `workers/provisioning` fails** as packaged
   (module not found); the tests pass by file.
5. **`tenants:admin` is an account-takeover credential** for any tenant: the
   owner door returns the set-password link. The static-bearer design cannot
   work against C8 (fifteen-minute cap, one audience per instance) and the
   minter route does not exist. See seam 6.
6. **C4 lacks `handoff` and `api`**, so decision 5 (operators) cannot work as
   built, and `issuer` means different things on the two sides. See seam 4.
7. Low: template table names from `information_schema` interpolated raw;
   `slice(0, 63)` on the database name with no collision check.

### WS-D — identity bridge

Verified: the verifier pins RS256, requires iss, aud, iat, exp and scope with
a fifteen-minute cap, answers 501 when unset and imports nothing from the
gateway door or the local secret; C6 migration; service token with a closed
scope set and no person claims; the handoff door resolves by subject then
confirmed email, refuses rebinding, spends the code atomically, answers one
401 for every failure; `/authorize` checks the allow-list before any redeem
and never carries the code onward; hub tiles through `/hub/open/:id` with the
membership check and token-bound licence read; the operator path. Auth 310
unit and 210 integration with none skipped; consumer 22 + 17 tests and
`smoke:handoff` 33; Strapi 85; console 59 and typecheck.

Defects the Left list does not mention:

1. **High.** `requireInternalKey` leaves `/internal/*` open when
   `INTERNAL_API_KEY` is unset outside production. On the dev estate anyone
   who can reach auth mints an operator session for any subject. The live
   walkthrough must not run without the key set; the middleware should refuse
   when unset in every environment.
2. **Medium.** `POST /internal/handoff` takes `instance.url` and `instance.api`
   from the body with no check against the tenant-instance record: past the
   key, auth will post a freshly signed token to any origin.
3. **Medium.** The code is bound to `db` only, not to origin, state or
   session, unlike management's own handoff, which binds all three.
4. **Medium.** Migration 112 returns silently when `up_users` is absent and is
   recorded as applied, so on a fresh database the column can be missing for
   ever and every handoff 500s. The repo's `requires` mechanism exists for
   this.
5. `storeSessionAllowance` not called; the operator's subject is found only
   through the third fallback. `/operator` page has no test. `GET /hub/open`
   mints on a GET with no CSRF token; the redeem route is unauthenticated,
   unlimited, and scans every tenant when `db` is absent.
6. Undisclosed edits: auth `app.js`, `container.js`, `internal.routes.js`, and
   Strapi `src/estate/bridge.js` in WS-C's directory.

### WS-E — Sign's platform half

Verified: C9 routes exactly, validated both ways against the pack; the JWS
over three claims with its own key and kid; the fence as described; staff
routes and console wiring; the seam mapping; budgets; esign out of the
harness and README. `check:sign` 62 checks (the report said 58), contracts 14,
console and gateway typecheck, `smoke:sign` stand-in with section W 12 of 12.

Defects the Left list does not mention:

1. **High. The gateway test suite fails.** `gateway/src/anonymous.test.ts`
   still asserts the sign routes are anonymous; the report substituted
   "gateway typecheck" for the suite its own change breaks.
2. **High. rutba.io's verify page is dead now.** It fetches the gateway path
   WS-E removed and links a dead JWKS. Not WS-E's file; WS-E's change.
3. **High. Cross-instance impersonation.** Any holder of the one estate-wide
   token can name another instance in the header and file countersigns or
   read, file and cancel formalities under that organisation. Admitted as a
   known limit; the countersign route also carries `audit: false`.
4. **Medium. The shared env pair is a trap.** Setting `RUTBA_PORTAL_API_URL`
   to Strapi as the spec said breaks usage metering silently (billing loss)
   and the feedback relay. The seam should read `RUTBA_SIGN_PLATFORM_*` only.
5. Medium: `@rutba/contracts` pinned to `0.3.0` in Strapi's package while
   every other workspace uses `*`. Low: the 503-no-key path is untested; the
   public verify body is deliberately not the pack's verify-response shape.
6. Undisclosed: `src/gates/limits.js`, the consumer smoke script.

## Process failures, and the rules added to README.md

A migration applied to the shared dev database from an unmerged worktree; two
streams taking the same migration ordinal; concurrent `smoke:sign` runs
deleting each other's rows; every stream editing files outside its list, two
of them without saying so; two helpers shipped as fulfilled promises with no
caller. The five rules now at the end of README.md address each.

  recovery doors by mode; an aggregate storage cap; bound or drop operator

  `registerOwnerRelation` for Sign's two columns; write Sign's proof under the

- **WS-B.** Gate keys and policy reads; backfill `owner_user_id`; invert

- **WS-D.** Fail closed on `/internal/*` when the key is unset; bind

## Decisions for the owner, consolidated

1. **Sign for individuals** is the first offered product after Drive and
   Workspace: yes?
2. **The `tenants:admin` credential**: minted per call by auth for one
   instance's audience (recommended), or a static bearer, which needs the
   verifier's cap lifted for that scope.
3. **Key per instance** for the sign-instance gate, now (recommended) or
   later.
4. **The shared env pair** keeps its gateway meaning; the seam reads its own
   variables only (recommended).
5. **rutba.io's verify page**: the gateway routes `/v1/public/sign` to Strapi
   (recommended, keeps the public API host stable), or a public Strapi host.
6. **The individual instance record**: `url` the launcher, an `authorize`
   origin for the consumer auth, `api` the core origin, product `sign`.
7. **Total storage** on the individual instance: a cap per person, or a pool.
8. **No owner-claim path** on an individual instance; operators only
   (recommended).
9. **Provisioning**: who builds the per-product template database
   (`stage_template` in `run-fleet.sh` proposed); suspension at the licence's
   expiry plus grace (built); dedicated instances by hand (built).
10. **Countersign key** as its own `SIGN_COUNTERSIGN_JWK` (built); **abuse
    intake** now or when a page exists; **live host** `app.sign.rutba.io`;
    the site's **taster** stays; "Start sending" carries `app: 'sign'`.
11. Mail, assistant and calendar for individuals: none proven; leave out of
    the first cut unless wanted.
12. WS-A's question: `RUTBA_CORE_MODE=individual` on the solo dev core, or a
    dev directory introduced deliberately.
