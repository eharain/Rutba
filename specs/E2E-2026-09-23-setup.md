### Added to `consumer/.env.development` (the only file the gateway-spawned core reads)

Appended after the three bridge names, which are unchanged and still there:

| Name | Value |
|---|---|
| `CORE__RUTBA_CORE_TENANTS` | `D:/Rutba2.0/consumer/.data/tenants.dev.json` |

| `CORE__RUTBA_EDGE_KEY` | a 24-byte hex value, machine-local (not reproduced here) |
| `CORE__RUTBA_CRED_KEY` | **the same 64 hex characters as `POS_STRAPI__MAIL_CRED_KEY`** |
| `CORE__PUBLIC_URL` | `http://localhost:4020` |

Two of those are not in the brief's list and both are load-bearing:

- **`CORE__RUTBA_EDGE_KEY`.** Without it a directory core believes no domain and
  refuses every request that names one, so **no tenant can be addressed without
  a token at all** — no `GET /api/setup/state` per tenant, and no registration
  on `individual_dev`. Nothing in the dev estate is a Caddy edge, so this is
  what a scripted call uses.
- **`CORE__PUBLIC_URL`.** On a directory core the confirmation link is
  `<PUBLIC_URL>/api/auth/email-confirmation/any`, a route only core serves.
  `POS_STRAPI__PUBLIC_URL` (`:4010`, legacy Strapi, unchanged) would 404 and
  would look for the code in the wrong tenant.

`CORE__RUTBA_CRED_KEY` is deliberately the **same value** as the existing
`POS_STRAPI__MAIL_CRED_KEY`: `RUTBA_CRED_KEY` outranks `MAIL_CRED_KEY` in
`api/legacy/strapi/src/utils/credentials/vault.js` and `decrypt` tries one key
only, so a fresh value would make every credential already sealed in `pos_db`
unreadable.

### 5.2 `GET /api/setup/state` answers for each tenant — PASS

How a tenant is addressed:

- **With a token**: the `db` claim core signed into it at sign-in. Nothing else
  is consulted, and the token wins over any domain.
- **Without a token**: `X-Rutba-Domain` plus `X-Rutba-Edge-Key`, matched against
  `CORE__RUTBA_EDGE_KEY` in constant time. The domain is looked up in the
  directory file. A domain with no key, or a wrong key, is `403`; a verified
  domain no tenant owns opens nothing; neither header opens nothing.
- **In the dev estate nothing sets those headers** (there is no Caddy edge and
  no app originates them — `packages/api-client` only forwards them). So a
  browser request carrying no token resolves **no tenant**: the journey threads
  address a tenant either with a token or by sending the two headers themselves.
  See Defect 2.

```
$ curl http://localhost:4020/api/setup/state                                  (no token, no domain)
  503 {"data":{"state":"unknown","setupOpen":false,"recoveryOpen":false,"mode":"organisation"}}

$ curl -H 'X-Rutba-Domain: individual.rutba.test' …/api/setup/state           (no edge key)
  403 {"error":{"status":403,"name":"ForbiddenError","message":"The request domain could not be verified"}}

$ curl -H 'X-Rutba-Domain: org.rutba.test' -H 'X-Rutba-Edge-Key: <key>' …     (-> pos_db)
  200 {"data":{"state":"ready","setupOpen":false,"recoveryOpen":false,"hosted":false,"mode":"organisation"}}

$ curl -H 'X-Rutba-Domain: localhost'       -H 'X-Rutba-Edge-Key: <key>' …    (-> pos_db)
  200 {"data":{… ,"mode":"organisation"}}
```

## Defects

1. **The individual-instance reconcile leaves the old record active.** (High
   for this programme.) `ensureIndividualInstance` finds its row by
   `tenantRef`, so moving `INDIVIDUAL_INSTANCE_DB` creates a second record and
   leaves the first `active`. The platform organisation now owns **two**
   instances labelled "Individuals" whose descriptor says `mode: individual`:
   id 47 → `pos_db`, id 106 → `individual_dev`. `individualInstance()` reads
   the environment's database name so the hub shows the right one, but
   `estate/bridge.js` takes an instance **by id** and only checks its mode
   (`modeOf(instance) !== INDIVIDUAL`), so a caller holding id 47 would open an
   **operator session against the organisation's database**. E2E-PAR's step 3
   must use id 106 / `document_id icg9twrcmzxxkm3gn0p4s63y` and nothing else.
   File: `management/api/legacy/strapi/src/estate/individual.js`, the
   `findOne({ … tenantRef: config.db … })` in `ensureIndividualInstance`.
   The fix for this estate is one row:
   `update tenant_instances set status = 'deleted' where id = 47;` — **not
   applied**: writing it was refused here as a change to a shared resource, and
   this thread does not work around a refusal. It is left for the owner.
2. **Nothing in the dev estate can address a tenant without a token.** (High
   for the journeys.) Under directory tenancy a no-token request needs
   `X-Rutba-Domain` + `X-Rutba-Edge-Key`; there is no Caddy edge in dev and no
   app originates the pair (`packages/api-client/lib/forward-headers-server.js`
   only forwards what arrives). A browser request that carries no token reaches
   core with no tenant, and the first handler to ask for a database gets
   `NoTenantContextError`. Sign-in is unaffected (it names the database in the
   body, and the chooser of 5.4 proves it), but nothing a signed-out visitor
   does can say which tenant it is for. E2E-IND must register with a scripted
   call carrying the two headers, as 5.5 does.
   **And there is no registration screen to begin with**: `console/apps/auth`
   has `login`, `authorize`, `logout` and the launcher, and nothing in any
   consumer app posts to `/api/auth/local/register` — the open door of
   individual mode is API-only. E2E-IND's step 1 ("A registers at the
   individual instance's own sign-in") cannot be done in a browser on any
   estate, dev or otherwise, until that screen exists.
3. **The organisational register door is open on the dev tenant.** (High,
   pre-existing.) `pos_db`'s own `allow_register` is `true`, and round two's
   finding 5 — the organisational door takes `app_roles` ids from the body —
   therefore applies to it live: a stranger who can reach core with the
   `pos_db` domain can grant themselves any active role id in that database,
   and its catalogue holds 47 `_staff` keys. Not changed here (it pre-existed
   and `pos_db` is not this programme's to alter).
4. **An individual database made from an organisation's template keeps the
   organisation's role catalogue.** (Medium.) `individual_dev` carries 160
   `api_pro_app_roles`: the 6 `_individual`/`platform_operator` keys the seeder
   added, **and the 47 `_staff` keys that came with `tpl_sign`**, because the
   seeder adds and updates but never prunes (its own note: "1 row(s) no
   descriptor declares any more — run … --prune"). Decision 4 says role sets
   are exclusive by mode. Nothing grants them today — the individual
   registration door refuses a body that names roles at all — but they are
   there to be granted, and with defect 3's shape they would be reachable if a
   mode ever took ids from a body.
5. **A solo core's file locations do not survive the switch by themselves.**
   (Low, documented.) Turning directory tenancy on moves every location under
   `<root>/<db>`, so an existing deployment's uploads, Drive blobs, Workspace
   drafts and recovery token are silently elsewhere unless its entry names
   them. `consumer/docs/tenancy-directory.md` describes the mechanism but the
   "Not done yet" list does not warn that switching a live tenant needs its
   four paths written into its entry. This record's `pos_db` entry is the
   worked example.
