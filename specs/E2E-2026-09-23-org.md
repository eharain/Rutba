## Step 1 — register at management auth, confirm, sign in, convert the organisation

**Registration: PASS. Confirmation: BLOCKED. Everything after it: BLOCKED.**

The sign-up screen the portal site links to is served by management auth
itself, so the absence of the portal site did not block this part:
`http://localhost:4101/signup?from=portal&app=portal`, page id
`localhost · AUTH-SIGNUP-FORM`. The form took a name, an address and a
password and answered with the page `AUTH-SIGNUP-SENT` ("Check your email",
request id `fca37fc3`), as a real signup does.

What it wrote, read back from management Strapi's Postgres
(`scratchpad/e2e-org/out/s1-read.txt`):

```
{"id":178,"username":"e2e-org-0145-owner@rutba.test","email":"e2e-org-0145-owner@rutba.test",
 "confirmed":false,"blocked":false,"provider":"local","created_at":"2026-09-23 01:49:39.454"}
```

and the backend logged it (`http://localhost:4999/log/management-strapi`):

```
[2026-09-23 01:49:48.702] http: POST /api/identity/register (9621 ms) 202
```

The password this thread chose is the one on that row, proved by the two
answers being different rather than by reading anything
(`scratchpad/e2e-org/out/s1-signin.txt`):

```
sign-in, the password this thread chose : 403 {"error":{"code":"EMAIL_NOT_VERIFIED", …}}
sign-in, a different password           : 401 {"error":{"code":"INVALID_CREDENTIALS", …}}
global auth POST /v1/auth/login         : 403 EMAIL_NOT_VERIFIED, request id 29cc0e53-…
```

**Where it stops.** The address cannot be confirmed on this machine.

- The confirmation link is mailed by management Strapi through a relay and
  `rutba.test` bounces; the estate's email provider is `sendmail`
  (`[email] The "sendmail" email provider is still supported …`, the boot
  warning in the backend log), so nothing writes the link to a log the way the
  consumer instances do. `POST /api/identity/confirmation/resend` answers `202`
  and changes nothing that can be read from here.
- The programme's documented way round it — set `confirmation_token` on the
  person's `up_users` row to the sha256 of a code you choose and open
  `/verify?code=<code>` on management auth — is a write to the shared
  management database, and **this machine refused it** ("Modify Shared
  Resources"). This thread does not work around a refusal.

For the owner, this is the whole of it. On
`postgresql://…@localhost:5432/rutba_strapi` (the name and credential are in
`management/api/legacy/strapi/.env`):

```
-- choose a code, e.g. CODE=$(openssl rand -hex 16)
update up_users
   set confirmation_token = <the sha256 hex of CODE>
 where id = 178;            -- e2e-org-0145-owner@rutba.test
```

then open `http://localhost:4101/verify?code=<CODE>` in a browser. That route
(`management/auth/src/http/routes/discovery.routes.js`, `router.get('/verify')`)
hands the code to Strapi's `POST /api/identity/confirm`, which confirms the
address, onboards the person into an organisation of their own and sends them
to `/login?confirmed=1`. Nothing else is needed: the account, its password and
its marker are already in place.

The rest of this step — signing in, the personal organisation onboarding
creates, and converting it to a team organisation — is **BLOCKED** behind that
confirmation. Sign-in refuses an unverified address (the three answers above),
so there is no session, no hub and no organisation row to convert.

What the conversion would have been, from WS-C's walkthrough
(`management/api/legacy/strapi/scripts/provisioning-walkthrough.js`, the `buy`
step): onboarding makes every organisation `kind: 'personal'`, a personal
organisation is shown the one shared individual instance as its only workspace
(C4) and the provisioning reaction refuses to build it a space of its own, so
the walkthrough turns it into a company with one update —
`update organizations set kind = 'team', name = … where id = <the org row>` —
and says in its own comment that nothing in the estate does this for anybody.
**It is manual, and it is a database write**, which is the same refusal as
above; it is also the round-two review's open decision 5.
