The password this thread chose is the one on that row, proved by the answers

**Where it stops.** The address cannot be confirmed on this machine.

- Management Strapi sends its mail over SMTP to an external relay
  (`MAIL_TRANSPORT=smtp` in its `.env`) and `rutba.test` bounces. Unlike a
  consumer instance it has no log mode, so no link is written anywhere a
  tester can read. `POST /api/identity/confirmation/resend` answers `202` and
  changes nothing readable.
- The programme's documented way round it — set `confirmation_token` on the
  person's `up_users` row to the sha256 of a code you choose and open
  `/verify?code=<code>` on management auth — is a write to the shared
  management database, and **this machine refused it** ("Modify Shared
  Resources"). This thread does not work around a refusal.

For the owner, this is the whole of it. On the management Strapi database
(`DATABASE_URL` in `management/api/legacy/strapi/.env`):

```
-- choose a code, e.g. CODE=$(openssl rand -hex 16)
update up_users
   set confirmation_token = <the sha256 hex of CODE>
 where id = 178;            -- e2e-org-0145-owner@rutba.test
```

then open `http://localhost:4101/verify?code=<CODE>`. That route
(`management/auth/src/http/routes/discovery.routes.js`, `router.get('/verify')`)
hands the code to Strapi's `POST /api/identity/confirm`, which confirms the
address, onboards the person into an organisation of their own and sends them
to `/login?confirmed=1`. The account, its password and its marker are already
in place; nothing else is needed to restart this thread at step 1's second
half.

The rest of the step — signing in, the personal organisation onboarding
creates, and converting it to a team organisation — is **BLOCKED** behind that
confirmation. Sign-in refuses an unverified address (the three answers above),
so there is no session, no hub and no organisation row to convert.

What the conversion would have been, from WS-C's walkthrough
(`management/api/legacy/strapi/scripts/provisioning-walkthrough.js`, its `buy`
step): onboarding makes every organisation `kind: 'personal'`, a personal
organisation is shown the one shared individual instance as its only workspace
(C4) and the provisioning reaction refuses to build it a space of its own, so
the walkthrough turns it into a company with one update —
`update organizations set kind = 'team', name = … where id = <the org row>` —
and says in its own comment that nothing in the estate does this for anybody.
**It is manual, and it is the same kind of shared-database write**; it is also

## Step 4 — the owner's set-password link from the instance log

**BLOCKED**, on step 2: no instance was provisioned, so no instance mailed

Two things about that link are worth recording anyway, because the programme
tells every thread to read instance mail from the gateway's log and **that
does not work**:

- A consumer instance in log mode writes one line per message and it carries
  the recipient and the subject only —
  `[email] (log mode) to=… subject="Account confirmation"` — never the body,
  the link or the token. The message is kept in an in-process array that
  nothing outside the process can read
  (`consumer/api/platform/src/email.js`, the `log` branch around line 111).
  Three such lines are in `http://localhost:4999/log/erp-core` for the
  accounts this thread made, with no link between them. Defect 2.
- The way that works, and the way E2E-SETUP used, is to read the token out of
  the tenant's own row (`up_users.confirmation_token`,
  `up_users.reset_password_token`) and open the route the link would have
  carried. That is a read, and it is what step 5 below did.

## Defects

1. **No management account can be confirmed on this estate, so every journey
   that needs a management sign-in stops at the first step.** (High.) Mail goes
   over SMTP to an external relay and `rutba.test` bounces; management Strapi
   has no log mode, so nothing writes the link where a tester can read it; and
   the documented substitute is a write to the shared management database,
   which this machine refuses. Steps 1 (second half) to 4 and 6 are blocked by
   this one fact. Evidence: the `202` from register and from
   `confirmation/resend`, `403 EMAIL_NOT_VERIFIED` at both sign-in doors, and
   the statement above that would clear it.
2. **An instance's mail in log mode records only who it was for.** (Medium.)
   `consumer/api/platform/src/email.js`, the `log` branch (around line 111),
   prints `to=` and `subject=` and pushes the message into an in-process array;
   the link, the token and the body reach nothing a person can read. The
   programme tells every thread to read instance links from the gateway's log,
   and no thread can. The way round it is a read of the tenant's own row, which
   is what this record did and what the setup record did before it.
3. **A person who registers themselves on the organisational tenant can read
   and write real business records.** (High, pre-existing; the live shape of
   round-two finding 5 and setup defect 3.) The register door grants
   `storefront_user`, and that role's policy map allows create, update, delete
   or publish on eight content types including `cms-page`, `cms-footer`,
   `site-setting` and `customer`; `GET /api/customers` returned all 41
   customers of the dev tenant, with names and telephone numbers, to an account
   made two minutes earlier. `pos_db`'s `allow_register` is `true`, so anybody
   who can address that tenant can have such an account. No write was made by
   this thread. Evidence: `e2e-org/out/s7-perms.txt`, `permissions.json`.
4. **The app door and the API door disagree about the same account.** (Medium.)
   The consumer auth app refuses the sign-in outright — "Your account does not
   have the required role. Contact your administrator." — while
   `POST /api/auth/local/any` mints that same person a token for `pos_db`,
   after which defect 3 is reachable. The role check that protects the launcher
   is not on the token door behind it.
5. **The Sign app's public verify page answers a signed-out visitor "No active
   session".** (Medium.) The page says verification needs no account; a digest
   pasted into it lands on `/verify/<digest>` (`SUITE-SIGN-VERIFY`) and renders
   a red "No active session" rather than valid, tampered or unknown. The core
   answered `400 NoTenantContextError` and then `200` for the same path in the
   same render. This is not the round-two finding about rutba.io's verify page:
   that one is the portal site's, this one is the instance app's.
6. **Nothing in a browser can name its tenant on a no-token route.** (High,
   **expected — setup defect 2.**) `GET /api/sign/public/verify/<digest>` with
   no headers is `400 NoTenantContextError`; with the domain and the edge key
   it is `200`. Recorded here only because it reaches a route meant for the
   public, and is the likely cause under defect 5.
7. **A confirmed address on the dev organisation lands on a dead port.** (Low,
   pre-existing setting.) `pos_db`'s confirmation redirect is
   `http://localhost:4000/login?confirmed=1`; the storefront is asleep in this
   profile and nothing in the suite the person was confirming for lives there.
8. **Half the programme's pages are not in the profile the estate runs.**
   (Medium, process.) The portal site, the portal console and the management
   console are `portal`/`full` services; the running profile is `erp`, so the
   steps that name those pages cannot be run in a browser at all, and this
   thread drove the routes behind them instead. The management API gateway on
   4100 is in the profile and woke on demand, which is how the platform verify
   path was proved.
9. **`pagination[limit]` was ignored** on `GET /api/customers` — a request for
   three rows answered with a page of 25 and
   `{"pagination":{"page":1,"pageSize":25,"pageCount":2,"total":41}}`. (Low.)
